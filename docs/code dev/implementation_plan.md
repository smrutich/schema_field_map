## Constraint Compliance Summary

The challenge prohibits passing both full schemas to an LLM in a single prompt. This pipeline satisfies that constraint at every stage:

| Stage | What the LLM Sees |
|---|---|
| Semantic Profiling | One field at a time — no cross-schema exposure |
| Table Routing | Table/collection names only — no fields from either schema |
| Field Mapping | One source field + top-3 retrieved candidates only |
| Transformation Extraction | One confirmed field pair at a time |
| Relationship Validation | FK metadata only — no raw schema dumped |

## Step 1 — Define All Pydantic Models (Contract-First)

**Implement before any pipeline logic. Every node's input and output is typed against these models.**

---

### 1.1 SourceField

Represents a single parsed field from the MySQL schema.

Fields to include:
- `table_name` — which of the three source tables
- `field_name` — raw SQL column name
- `sql_type` — full type string including length/precision (e.g. `DECIMAL(12,2)`)
- `nullable` — boolean derived from `NOT NULL` constraint
- `constraints` — list of strings: `PRIMARY KEY`, `UNIQUE`, `FK -> table.field`
- `comment` — inline comment from the schema (critical for semantic meaning)
- `text_repr` — computed string concatenating all of the above for embedding

> **Why `text_repr` matters:** `rec_stat`'s comment (`A=Active, I=Inactive, T=Terminated`) is what allows the embedding model to surface `employment.status` as the top candidate — not the field name itself.

---

### 1.2 DestinationField

Represents a single flattened field from the MongoDB schema.

Fields to include:
- `collection_name` — which of the three target collections
- `path` — dot-notation path (e.g. `fullName.firstName`, `employment.isRemote`)
- `bson_type` — MongoDB type string
- `comment` — inline comment from the schema
- `text_repr` — same construction as `SourceField.text_repr`

> **Flattening rule:** All nested sub-documents must be fully flattened to dot-notation at parse time. `fullName.firstName`, `employment.status`, `department.departmentId` are all individual `DestinationField` entries.

---

### 1.3 SemanticProfile

Generated by the LLM during profiling — one per field.

Fields to include:
- `entity` — top-level business entity (e.g. `employee`, `department`)
- `concept` — what this field represents (e.g. `identifier`, `status`, `timestamp`)
- `business_meaning` — one plain English sentence explaining the field's purpose
- `keywords` — list of synonyms and related terms (used to enrich the `text_repr` before embedding)

> **Design decision:** `SemanticProfile` outputs are merged back into each field's `text_repr` before embedding. This enrichment step meaningfully improves retrieval quality for abbreviated or cryptic field names like `emp_cd`, `dept_head_id`, or `cost_ctr_cd`.

---

### 1.4 CandidateMatch

Output of the retrieval stage — one per candidate per source field.

Fields to include:
- `destination_field` — dot-notation path of the candidate
- `embedding_similarity` — raw cosine similarity score
- `lexical_similarity` — RapidFuzz token sort ratio score
- `hybrid_score` — weighted combination: `0.8 × embedding + 0.2 × lexical`
- `retrieval_confidence_prior` — categorical: `HIGH`, `MEDIUM`, or `LOW` based on hybrid score thresholds

> **Why hybrid scoring:** Abbreviated field names like `f_name` and `l_name` have weak embedding overlap with `firstName` and `lastName`. Lexical similarity on token components catches these cases that pure embedding retrieval misses.

---

### 1.5 FieldMapping

The core output unit. Instructor enforces this on every LLM mapping call.

Fields to include:
- `source_field` — original field name (not dot-notation, just the column name)
- `destination_field` — dot-notation path, or `null` if no appropriate match
- `type_transform` — must match pattern `SOURCE_TYPE -> DEST_TYPE`
- `confidence` — float, validated strictly between `0.0` and `1.0`
- `reasoning` — single plain English sentence, validated between 5 and 200 characters
- `notes` — nullable string for value transform logic (e.g. `A -> active, I -> inactive, T -> terminated`)
- `relationship_validated` — boolean, set to `True` by the validation node if FK alignment confirmed

---

### 1.6 TableRoutingDecision

Output of the routing LLM call.

Fields to include:
- `source_table` — one of `emp_master`, `dept_info`, `locations`
- `destination_collection` — one of `employees`, `departments`, `locations`
- `confidence` — float, validated between `0.0` and `1.0`
- `reasoning` — plain English sentence

---

### 1.7 TransformationRule

Output of the transformation extraction node.

Fields to include:
- `source_field` — column name
- `destination_field` — dot-notation path
- `transform_type` — categorical: `VALUE_MAP`, `TYPE_CAST`, `ID_STRATEGY`, `FORMAT_CHANGE`, `NONE`
- `transform_logic` — explicit description of the transform or null
- `example` — a before/after value pair illustrating the transform

> **Why a separate model:** Keeping transformation logic separate from the mapping decision improves consistency. The mapping LLM focuses on *which* field to map to; the transformation LLM focuses on *how* to convert the value. Conflating both into one call produces less reliable `notes` fields.

---

### 1.8 TableMapping

Aggregated output per source table → destination collection pair.

Fields to include:
- `source_table`
- `destination_collection`
- `confidence` — mean of all child `FieldMapping.confidence` values
- `reasoning` — sourced from the routing decision
- `field_mappings` — list of all `FieldMapping` for this table
- `unmapped_source_fields` — list of source field names with no confirmed mapping
- `unmapped_destination_fields` — list of destination paths selected by no source field

---

### 1.9 FinalOutput

Top-level output document.

Fields to include:
- `mapping_version` — hardcoded `"1.0"`
- `source` — `"legacy_hrm (MySQL)"`
- `destination` — `"people_platform (MongoDB)"`
- `generated_at` — ISO 8601 timestamp populated at assembly time
- `tables` — list of `TableMapping`

---

### 1.10 Validation Rules Summary

| Field | Rule | Enforcement |
|---|---|---|
| `confidence` | `ge=0.0`, `le=1.0` | Pydantic `Field()` |
| `reasoning` | `min_length=5`, `max_length=200` | Pydantic `Field()` |
| `destination_field` | Regex `^[A-Za-z_][A-Za-z0-9_.]*$` or `null` | Pydantic `field_validator` |
| `type_transform` | Regex `.+\s->\s.+` | Pydantic `field_validator` |
| `unmapped_*` lists | Default to `[]` — never `null` | Pydantic `default_factory` |
| `generated_at` | Must be valid ISO 8601 datetime | Pydantic `datetime` type |
| `hybrid_score` | Must equal `0.8 × emb + 0.2 × lex` | Pydantic `model_validator` (post) |

---

### New Step 1.11 — Schema Format Conversion

**Node name:** `convert_raw_schema_to_json`

**What it does:**
- Reads raw schema files (your current format with inline comments)
- Uses regex patterns to parse field definitions
- Extracts: type, constraints, comments
- Outputs valid JSON files that conform to the structure shown earlier
- Validates output JSON before passing to Step 5 (`parse_schemas`)

**LLM calls:** None (deterministic)

**Implementation:** Pure Python regex + string parsing

## Step 2 — Configure Snowflake Cortex Client

### 2.1 Credential Management

Store all credentials as environment variables — never hardcoded:

- `SNOWFLAKE_ACCOUNT`
- `SNOWFLAKE_USER`
- `SNOWFLAKE_PASSWORD`
- `SNOWFLAKE_ROLE`
- `SNOWFLAKE_WAREHOUSE`
- `SNOWFLAKE_DATABASE`
- `SNOWFLAKE_CORTEX_URL`

Load at startup via `pydantic-settings` `BaseSettings` model so missing variables raise a clear startup error before any pipeline execution begins.

---

### 2.2 Instructor-Patched Client Setup

- Instantiate an OpenAI-compatible client pointed at the Snowflake Cortex REST endpoint
- Patch with `instructor.patch()` — this intercepts every call and appends Pydantic validation errors to the retry prompt automatically
- Set `max_retries=3` on the instructor patch — sufficient for recovering from malformed JSON without infinite loops
- Create **two separate patched client instances** — one configured for `snowflake-arctic-instruct` (routing, profiling) and one for `mistral-large` or `llama3-70b` (field mapping, transformation extraction) — model choice matters per task

---

### 2.3 Model Selection Rationale

| Task | Recommended Model | Reason |
|---|---|---|
| Semantic Profiling | `snowflake-arctic-instruct` | Structured factual extraction, low temperature |
| Table Routing | `snowflake-arctic-instruct` | Simple classification task |
| Field Mapping | `mistral-large` or `llama3-70b` | Requires nuanced semantic reasoning |
| Transformation Extraction | `mistral-large` | Requires value-level logic generation |
| Relationship Validation | No LLM — rule-based only | FK metadata is deterministic |

## Step 3 — Configure Embedding Model

- Use `sentence-transformers` with `all-MiniLM-L6-v2` — runs locally, no API cost, sufficient for schema-sized embedding tasks
- Embed destination fields **once** at startup and store the matrix in state — all subsequent source field lookups query this pre-built matrix
- Embed source fields **on-demand** during candidate retrieval — avoids holding a large matrix for both sides simultaneously
- Use `numpy` `dot` product on normalized vectors for cosine similarity — fast and dependency-light at this scale
- Install `rapidfuzz` for the lexical similarity component of hybrid scoring

---

## Step 4 — Define LangGraph State

The state object is the single source of truth passed between all nodes. Define as a `TypedDict` with all fields typed against the Pydantic models from Step 1.

State fields:

- `source_fields` — list of parsed and enriched `SourceField` objects
- `destination_fields` — list of parsed and flattened `DestinationField` objects
- `semantic_profiles` — dict keyed by `table_name.field_name`, value is `SemanticProfile`
- `destination_embeddings` — numpy matrix of embedded destination `text_repr` strings
- `destination_field_index` — list of destination paths in the same order as the embedding matrix rows (needed for lookup after similarity search)
- `table_routing` — list of `TableRoutingDecision`
- `candidate_matches` — dict keyed by `table_name.field_name`, value is list of `CandidateMatch`
- `field_mappings` — list of completed `FieldMapping` objects (grows across map_fields execution)
- `transformation_rules` — list of `TransformationRule` objects
- `table_mappings` — list of assembled `TableMapping` objects
- `final_output` — completed `FinalOutput` object or `None` until assembly
- `errors` — list of error dicts for failed fields — pipeline never halts on individual field failure

## Step 5 — Node: `parse_schemas`

**LLM calls: None**

### Responsibilities

- Load Dataset A and Dataset B from their source definitions
- For Dataset A: iterate each table, then each column — construct one `SourceField` per column, extracting type, nullability, FK references, and inline comments
- For Dataset B: flatten all nested sub-documents into dot-notation paths — `fullName.firstName`, `employment.isRemote`, `meta.createdAt` — each becomes its own `DestinationField`
- Build an initial `text_repr` for each field: concatenate table/collection name + field name + type + constraints + comment
- Write `source_fields` and `destination_fields` into state

### Special Cases to Handle at Parse Time

- `emp_id → _id`: flag as primary key requiring ID generation strategy
- `dept_id` as FK in `emp_master`: note that it maps to **both** `department.departmentId` (reference) and the denormalized `department.code` / `department.name` embedded fields — parse this as a multi-destination candidate
- `mgr_emp_id`: self-referential FK — note in constraints that the target collection is the same `employees` collection

---

## Step 6 — Node: `build_semantic_profiles`

**LLM calls: 2–3 batched calls (one per source table to minimize calls)**

### Purpose

Generate enriched business meaning for each field independently, without any cross-schema exposure. The profile output is then merged back into each field's `text_repr` before embedding — this is the single biggest quality improvement over a basic embedding approach.

### Prompt Design

- System message: domain expert in HR data systems
- Input per call: a batch of source fields from one table (field name + type + comment only)
- Instructor output: `List[SemanticProfile]`
- No destination schema information is present in this prompt

### Profile Usage

After profiling, update each `SourceField.text_repr` to include `business_meaning` and `keywords` from the profile. The enriched `text_repr` is what gets embedded in Step 7.

### Example Impact

`emp_cd` with comment `human-readable employee code` + profile keywords `["employee identifier", "HR code", "staff number"]` will embed much closer to `employeeCode` than the raw field name alone would.

---
## Step 7 — Node: `embed_destination_fields`

**LLM calls: None**

### Responsibilities

- Take all `destination_fields` from state
- Call the embedding model on each field's `text_repr`
- Stack results into a single numpy matrix
- Store matrix in state as `destination_embeddings`
- Store the parallel list of destination paths as `destination_field_index`

### Note on Timing

This node runs **after** profiling but **before** any source field embedding. Destination fields do not get a semantic profiling pass — their MongoDB field names and comments are already descriptive enough that raw `text_repr` embedding is sufficient. If schema quality were lower, you would add a destination profiling pass as well.

---

## Step 8 — Node: `route_tables`

**LLM calls: 1**

### Purpose

Establish which source table maps to which destination collection before any field-level work begins. This scoping step is what restricts candidate retrieval to the correct collection in the next node.

### Prompt Design

- Input: list of source table names + one-line descriptions (no fields)
- Input: list of destination collection names + one-line descriptions (no fields)
- Instructor output: `List[TableRoutingDecision]`
- Model: `snowflake-arctic-instruct`

### Constraint Compliance

This is the only LLM call where content from both schemas appears in the same prompt — but it contains **only table/collection names**, not field definitions. This satisfies the constraint.

### Expected Output

```
emp_master    →  employees      (confidence: 0.99)
dept_info     →  departments    (confidence: 0.99)
locations     →  locations      (confidence: 0.99)
```

This is a straightforward routing for this specific dataset, but the node must be implemented correctly to handle ambiguous cases in general (e.g. two source tables mapping to one collection).

---

## Step 9 — Node: `retrieve_candidates`

**LLM calls: None**

### Process (Per Source Field)

1. Embed the source field's enriched `text_repr` on-demand
2. Compute hybrid score against all destination embeddings:
   - Cosine similarity between source embedding and each destination embedding row
   - RapidFuzz `token_sort_ratio` between source field name and each destination path
   - Combined: `hybrid_score = 0.8 × cosine + 0.2 × lexical`
3. Filter candidates to only those in the destination collection assigned by the routing node
4. Take top-3 results above the similarity threshold of `0.40`
5. Assign `retrieval_confidence_prior`:
   - `hybrid_score > 0.90` → `HIGH`
   - `hybrid_score 0.75–0.90` → `MEDIUM`
   - `hybrid_score < 0.75` → `LOW`
6. If zero candidates pass threshold → flag source field as candidate for `unmapped_source_fields` and skip it in the mapping node

### Why 0.40 Threshold

Below 0.40, candidates are semantically unrelated. Forcing the mapping LLM to evaluate an irrelevant candidate set produces low-confidence, unreliable mappings and wastes LLM calls. It is better to mark the field unmapped and flag for human review.

### State Output

`candidate_matches` dict with `table_name.field_name` as key and list of `CandidateMatch` as value.

---

## Step 10 — Node: `map_fields`

**LLM calls: 5–10 (batched)**

### This is the primary reasoning node.

### Prompt Design (Per Call)

- System message: schema migration expert, HR domain context, instructed to prefer precision over guessing
- Source field block: table, field name, SQL type, nullable, constraints, comment
- Candidate block: top-3 candidates with path, BSON type, comment, hybrid score, and `retrieval_confidence_prior`
- Explicit instruction: select exactly one candidate, or return `destination_field: null` if none are appropriate
- No output format instructions in the prompt — Instructor handles this entirely via `response_model`

### Batching Strategy

Group up to 5 source fields per LLM call when:
- All 5 fields belong to the same source table
- Their top-3 candidate sets are **disjoint** (no shared destination paths)

If candidate sets overlap (two source fields competing for the same destination field), process individually. Overlapping sets require the LLM to implicitly rank competing claims, which degrades output quality.

Use `response_model=List[FieldMapping]` for batched calls, `response_model=FieldMapping` for individual calls.

### Retry Behavior

Instructor automatically retries up to 3 times on Pydantic validation failure, appending the validation error to the prompt. If all 3 retries fail, log the error to `state["errors"]` and mark the field as unmapped — **never halt the pipeline**.

### Special Cases to Call Out in the Prompt

For fields where the mapping is non-obvious, add a context hint:

- `emp_id → _id`: mention that INT primary keys require an ObjectId generation strategy and the original should be preserved as a legacy field
- `rec_stat`: the `CHAR(1)` code system should be called out explicitly so the LLM knows to produce a value map in `notes`
- `dept_id` in `emp_master`: hint that this FK maps to both a reference ID and denormalized name/code fields in the embedded sub-document

---

## Step 11 — Node: `derive_transformations`

**LLM calls: 1–2**

### Purpose

Extract explicit transformation logic for each confirmed mapping pair. This is kept as a **separate node** from `map_fields` deliberately — the mapping LLM focuses on *which* field to map to, and the transformation LLM focuses on *how* to convert the value. Conflating both into one call produces less reliable `notes` output.

### Input Per Call

A batch of confirmed `(source_field, destination_field)` pairs where transformation logic is non-trivial. Fields with `type_transform = VARCHAR -> String` and no value mapping needed can be skipped (rule-based: `transform_type = NONE`, no LLM call required).

### Fields That Require LLM Transformation Extraction

| Source Field | Transform Type | Expected Output |
|---|---|---|
| `rec_stat` | `VALUE_MAP` | `A → active, I → inactive, T → terminated` |
| `dept_stat` | `VALUE_MAP` | `A → active, I → inactive` → mapped to boolean `isActive` |
| `is_remote` | `TYPE_CAST` | `TINYINT(1) 0/1 → Boolean false/true` |
| `emp_id` | `ID_STRATEGY` | `INT → ObjectId (generate new; store original as legacyId)` |
| `hire_dt` | `FORMAT_CHANGE` | `DATETIME → ISODate (UTC normalization required)` |
| `sal_currency` | `NONE` | `CHAR(3) ISO 4217 → String ISO 4217 — passthrough` |

### Output

`List[TransformationRule]` written to `state["transformation_rules"]`

These are merged back into the corresponding `FieldMapping.notes` during assembly.

---

## Step 12 — Node: `validate_relationships`

**LLM calls: None — fully rule-based**

### Purpose

Use FK metadata extracted at parse time to validate and boost confidence on mappings that align with relational structure. This is the most explainable confidence signal in the pipeline.

### Rules

- For each FK field in `source_fields` (identified by `FK -> table.field` in constraints), check that its `FieldMapping.destination_field` resolves to the expected reference field in the MongoDB schema
- If the FK target aligns correctly → set `relationship_validated = True` on the `FieldMapping` and apply a `+0.10` confidence boost (capped at `1.0`)
- If the FK target does not align → log a warning to `state["errors"]` but do not override the mapping — flag for human review instead

### FK Alignment Cases to Validate

| Source FK | Expected Destination |
|---|---|
| `emp_master.dept_id → dept_info.dept_id` | `employees.department.departmentId` |
| `emp_master.mgr_emp_id → emp_master.emp_id` | `employees.employment.managerId` |
| `emp_master.office_loc_id → locations.loc_id` | `employees.location.locationId` |
| `dept_info.parent_dept_id → dept_info.dept_id` | `departments.parentDepartmentId` |
| `dept_info.dept_head_id → emp_master.emp_id` | `departments.headEmployeeId` |

---

## Step 13 — Node: `assemble_output`

**LLM calls: None**

### Responsibilities

1. Merge `TransformationRule` outputs back into the `notes` field of each corresponding `FieldMapping`
2. Group all `FieldMapping` objects by source table
3. For each table group, compute `TableMapping.confidence` as the mean of all child field confidences
4. Identify `unmapped_source_fields`: source fields with no confirmed `FieldMapping` (from retrieval or persistent LLM failure)
5. Identify `unmapped_destination_fields`: destination paths that appear in no `FieldMapping.destination_field`
6. Construct `TableMapping` for each of the three table pairs
7. Build `FinalOutput` with current ISO 8601 `generated_at` timestamp
8. Run `FinalOutput.model_validate()` as a final structural gate — this is a Pydantic check independent of Instructor
9. Write `final_output` to state and serialize to `schema_mapping_output.json`

---

## Step 14 — Conditional Edge: `flag_for_review`

### Trigger Condition

Any `FieldMapping` with `confidence < 0.75` after relationship validation.

### What This Node Does

- Collects all low-confidence mappings from state
- Writes a separate `low_confidence_flags.json` file alongside the primary output
- Each flag entry includes: `source_field`, `destination_field`, `confidence`, `reasoning`, and `candidate_alternatives` (the other top-2 candidates that were not chosen)
- Does **not** modify `schema_mapping_output.json`

### Why Separate File

Low-confidence mappings are still written to the primary output — they are not suppressed. The flag file is an audit artifact for human review, not a replacement of the output.

### Edge Sequence

```
START → parse_schemas → build_semantic_profiles → embed_destination_fields
      → route_tables → retrieve_candidates → map_fields
      → derive_transformations → validate_relationships → assemble_output
```

### Conditional Edge After `assemble_output`

- If any `FieldMapping.confidence < 0.75` → also route to `flag_for_review`, then `END`
- If all confidences ≥ 0.75 → route directly to `END`

### Conditional Edge After `map_fields`

- If `state["field_mappings"]` is non-empty (at least partial success) → continue to `derive_transformations`
- If `state["field_mappings"]` is completely empty (total failure) → route to `error_handler`, raise structured exception with full `state["errors"]` log

## Key Design Decisions

| Decision | Rationale |
|---|---|
| Contract-first Pydantic models | Every node's I/O is validated before pipeline logic is written |
| Semantic profiling before embedding | Enriched `text_repr` dramatically improves retrieval for cryptic field names |
| Hybrid retrieval (embedding + lexical) | Embedding alone misses abbreviated names; lexical alone misses semantic equivalents |
| Table routing as scoped pre-filter | Eliminates cross-collection noise from candidate retrieval |
| Transformation extraction as separate node | Separation of concerns — mapping LLM picks the target; transform LLM describes the conversion |
| FK relationship validation as rule-based node | Deterministic and explainable — no LLM needed for structured metadata |
| Instructor with `max_retries=3` | Malformed outputs are recovered automatically without pipeline failure |
| LangGraph checkpointing | Failed nodes can be resumed without re-running upstream expensive steps |
| Individual error logging vs. halt | Field-level failures are captured and flagged without blocking the rest of the pipeline |
| Low-confidence review as separate artifact | Primary output is never suppressed; governance is handled as a parallel concern |
